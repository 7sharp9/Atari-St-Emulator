# Cadaver: mechanics

How the engine decides what the hero can touch, where a door leads, which room is live and how it reaches the screen, plus the route facts that fell out of driving the game: the road through level 0 and the first legs of level 1. The script language, the verb table, the action panel, the overlay and the loader are in `secrets.md`; sprites, tiles and the compositor are in `graphics.md`; the entity bytecode is in `ai.md`. This file points to those instead of repeating them.

**Conventions.** Addresses are runtime absolute addresses in the one-disk Empire build, where `A5 = $018152`; `N(A5)` is the field at `A5 + N`. The two-disk Replicants build (Disk 1 plus the Level disk) places the same structures `$100` bytes higher (`A5 = $0182b4`, the resource manager at `$4a566`, the object array at `$038438`), so a script that hard-codes an address from this file works on one build only; read `(A5)+96`, `(A5)+56` and `(A5)+164` from the snapshot instead. A bounding box is `[x lead, y lead, x trail, y trail]` in world units (8 units to a grid cell), so the hero reads `[25,23,19,17]` at the CAVERN start. Evidence labels: **driven natural** is joystick and keyboard input only, nothing poked or injected; **driven injected** names what was poked; **read** is code read but not run; **inferred** is a conclusion without a run behind it. A claim with no label was measured, and a count follows it where one exists.

**Hold timing.** One joystick packet starts a bounded, self-terminating move: it begins about 40,000 steps after the press, then covers one cell per about 25,000 steps in level 1 (10,000 in level 0), and a `kbd ff 02` packet from rest needs 60,000 to 100,000 steps to finish its 3 units. A hold begun while the hero is falling never moves, and a released direction keeps drifting for a while. Read a position only after the move has settled (one packet, at least 60,000 steps); a shorter budget catches the move in flight and looks exactly like a wall.

## 1. Rooms and the world grid

A level is a set of rooms laid out as rectangles on one shared world grid. A room is a **record in the type-3 resource** (section 2); the live room is the one `(A5)+164` points at, and `(A5)+1166` holds its slot number (a single word, written once per crossing at `$00727c`: 0 in CAVERN, 1 in TUNNEL). Rooms are not loaded from disk during play: all 72 level-0 rooms are resident from the boot load, and no code in the loaded image touches the FDC (none of the seven FDC and DMA register addresses `$ff8604`, `$ff8606`, `$ff8609`, `$ff860a`, `$ff860b`, `$ff860d`, `$ff860e` is named by an instruction of the image, and a traced crossing issues no trap and no FDC command).

**The room record** (`$6bf0a` for CAVERN, slot 0, 122 bytes; `$6bf84` for TUNNEL, slot 1, 32 bytes; the size grows with the object count):

| offset | meaning |
|---|---|
| `+1`, `+3` | x0, y0 of the room's rectangle on the world grid |
| `+4`, `+5` | width and height in grid cells (CAVERN 10 by 10, TUNNEL 3 by 5) |
| `+6..+19` | seven door slots, 2 bytes each, `$ffff` unused (CAVERN `[$32,$3b]`, TUNNEL `[$32,$33]`): ids in one global, sequential door namespace |
| `+20`, `+21` | FloorClampY and FloorClampX (6 and 6 in both rooms) |
| `+29` | the object count (TUNNEL 2, CAVERN 22 = `$16`); the room's type-5 id list has this many ids plus a terminating 0 (*inferred* from the two rooms; slot 71's list has no terminator) |

`+4` and `+5` are one pair read two ways: as the rectangle's size by the door resolver (section 4) and, minus 3, as a two-dimensional index into the `$5a10` table by `$00e7b0` (section 5). Every read of `+4` in the image agrees (`$00e7b0`, `$00cfc4`'s two sites, `$00de5e`); the read at `$00cd62` computes a value nothing uses.

**The world map** (`py/world_map.py`, `world_map.png`): of the 100 type-3 slots, 72 are populated, none of the 72 rectangles overlaps another, 99 pairs share a boundary edge and 18 touch at a single corner. TUNNEL is `[19,12]-[22,17]` and CAVERN `[12,18]-[22,28]`; they meet at `y = 17/18`, where the door `$32` lies. The adjacency graph of the rectangles is the room-connectivity map: a crossing never needs an explicit exit table, because the destination is found by position (section 4). The two-disk build's type-3 table is byte-identical slot for slot (`world_map.py` resolves the table pointers from each snapshot's `(A5)+96`, which is how the `$100` shift was found).

Level 1 has 97 rooms and 129 doors (`door_walk.py`); the Level disk of the two-disk build holds five levels (`secrets.md`, "Loading, the expander and the level directory").

## 2. The resource manager

`(A5)+96` points at an array of ten 18-byte rows, one per resource type 0 to 9: `+0` the index table, `+4` the data area, `+8` the byte count of the row's own data block, `+16` the entry count (word); `+12` is set at boot and by the level loader (role not read). An index entry is 4 bytes: a size and an offset, and the record is `data area + (entry & $1ffff)` (the offset is 17 bits: masking it to 16 misreads the type-2 templates from index 100 up, 155 of 255). Primitives:

- `$00c5a8` resolves `(type D0, index D1)` to `A0 = record`, `D0 = size`.
- `$00c52c` returns the row (`A1` index, `A2` data area); `$00c628` scans forward from `D1` for the next slot whose leading word is non-zero (`D1 = -1` on a miss) and `$00c660` scans backward. Callers that want a key wrap `$00c628` in their own compare-and-reloop (`$011256` is one).
- `$00c542`/`$00c56e` resolve an id to a record for the verb interpreter: a positive id is type 6, `$ffff` is the running actor `348(A5)`, any other negative is type 9 with the id taken from `2120(A5)`.
- `$00c696` builds all ten rows at boot from a table at `$57c8`, carving the index regions out of the pool at `(A5)+100` and the data regions out of `(A5)+44`, then clears them with `$00c6d0`. `$00b1e0`-`$00b52a` bulk-reloads types 2 to 7 from a memory stream; nothing in the image references it, by three techniques (`find_ram_callers.py`, `find_literal_ptr.py`, `find_jump_table_hit.py` over 303 constructible table bases).

| type | index table | data area | entries | content |
|---|---|---|---|---|
| 0 | `$4a51a` | `$4d65e` | 100 | not read |
| 1 | `$4a6aa` | `$4ea4a` | 100 | not read |
| 2 | `$4a83a` | `$5115a` | 255 | object class templates (class byte at `+22`) |
| 3 | `$4ac36` | `$6bf0a` | 100 | **rooms** (72 populated) |
| 4 | `$4adc6` | `$6d35a` | 400 | **door descriptors**, 8 bytes each; the same records are the flags that verbs 10 and 27 clear and set |
| 5 | `$4b406` | `$6dfda` | 100 | per-room object id lists, indexed by room slot |
| 6 | `$4b596` | `$6eb92` | 1000 | **objects** (1000 of 1000 populated); the live object state |
| 7 | `$4c536` | `$7550a` | 0 | shares type 8's index table, no entries |
| 8 | `$4c536` | `$7550a` | 64 | **the rucksack**, records `[object id][template idx]` |
| 9 | `$4c636` | `$7560a` | 10 | creature instances (empty until a script spawns one) |

(One-disk build, read off `room2_tunnel_entry.snap`; types 10 and above read as nonsense and are not rows.) The type-8 table looks empty in every snapshot taken before a pick-up because the rucksack is empty then; it is not a room registration table. The lever TUNNEL is object 144, record `$06fa0e` (`index[144] = $002c0e7c`); the sprite entry in the object array points at that record, so the "linked struct" of the collision code is the type-6 record itself.

**Save and restore** serialise types 3, 4, 5, 8 and 6 in that order behind the 4-byte magic `"CAD "` (`$44414320`): `$00c9c2` writes a row's byte count, those bytes and the whole index table at `A3`, `$00c9ee` is its mirror. The serialiser `$00b6e0` (via `$00b5a8`) runs automatically once at the start of every boot, from the boot menu `$0067ea` (no caller inside the image) before the restore prompt, dispatched on the byte `2518(A5)` (0 at first entry, `$01` after `$006962`); the restore side is `$00b8fc` (the magic compare) and `$00b94e`-`$00b968`. Nothing in play calls either. The price, the format step and the state block are in `secrets.md`, "Saving costs gold".

## 3. Movement and collision

There is no pixel probe and no collision mask. Walking is tested by `$008870` (`MovementStep_ObstacleCheck`) against the room's extent and the live object array, and the same call builds the list of nearby objects that drives the status bar and the icon panel (section 6).

**Call and footprint.** The walk loop (`$006e50`, called at `$006e78`/`$006e94`) recomputes the candidate position for each sub-step of a move from the direction vector table (`$5bea`, 16 dx/dy pairs) and calls `$008870` once per sub-step, so a long or diagonal move is checked incrementally. The routine is general: `$006d72` (a script-advance path) calls it too. Inputs: `D0`, `D1` the candidate x and y, `D2` the candidate z plus 1, `A0` the mover's descriptor (`52(A5)` for the hero), `A1` the identity object (`160(A5)`; the byte at `12(A1)` selects the mover kind, and kind 7 is the hero, *inferred*: no other mover has been seen at an edge). The footprint is built from the mover's own struct, not a constant:

```
trail x = D0 - A0.16 + 1      trail y = D1 - A0.18 + 1      top z = D2 + A0.20 - 1
```

The hero is a 7 by 7 box 30 units high (z 0 to 29 on the floor).

**Room extent.** The candidate fails to the portal check (section 4) when `D0 >= RoomMaxX(2238)`, `D1 >= RoomMaxY(2239)`, `D3 < FloorClampX(2204)`, `D4 < FloorClampY(2203)`, or `D4 > RoomMinY(2218)` while `D3 <= RoomMinX(2217)`. If the per-room selector `(A5)+140` is non-null, control also jumps through it into one of four inline quadrant tests (byte rectangles at `2222`-`2237`), and a failure of any of them goes to the portal check as well: an outer box with up to four corner cutouts gives a hand-painted, non-rectangular room its edge. Which quadrant is which corner, and what fills `(A5)+140` per room, is not read. TUNNEL's globals are `RoomMaxX 24`, `RoomMinX 2`, `RoomMaxY 40`, `RoomMinY 10`; CAVERN's `RoomMaxX` is 80.

**Object scan.** The object array is `(A5)+56`, count `(A5)+1152`, stride `$46` (70 bytes); TUNNEL has 2 entries (the hero and the lever) and CAVERN 22. Per entry, bytes 0-3 are the bounding box and bytes 4-5 the z range. A footprint that overlaps an entry in x, y and z:

- records a touch for the pair `(mover, object)` through the dedup cache `$00e614` (a 64-entry ring at `(A5)+512`, count `2146(A5)`, keyed on the two `+4` id words; a full cache is flushed by `$011788`), and a pair not seen before queues event 9 on the ring queue (section 7) as `[$9][object][id]` (the hero-contact paths `$006d90` and `$00934a` queue event 9 as well, but only for objects whose `+3` bit 6 says they have an event-9 block: `secrets.md`, "The type-6 record's state bytes");
- makes the object **solid** when byte 24 has its top bit set **or** bit 2 of byte 15 of the object's type-6 record (the sprite entry's `+10` pointer) is set: the result record then carries the marker `$fd`. The rule is an OR (`tst.b 24(A6) / bmi / btst #2,15(A2) / beq`). Walls are solid through byte 24; LOCK (verb 54) makes any object solid through `+15` bit 2 (callcap `$008868`: marker 0 to `$fd` on 4 of 4 objects when the bit is poked set) and UNLOCK (verb 55) reverses it. Objects that are neither stay walk-through: items (class 14), floor marks, and anything the hero overlaps without a solid bit.

A candidate that clears the extent and the scan ends with `D0 = -1`; a candidate outside the extent goes to `$008ac8`.

**The result record** at `(A5)+92` (`$038036`, one global address in every room): byte 0 is the count of overlapping objects, or the blocked status; byte 1 the solid marker `$fd`; then one 4-byte pointer per overlapping object (the sprite entry's `+10`), the nearest flagged with bit 7. The caller (`$007368`-`$0073da`) reads it after each accepted move and hands it to `$009440` (section 6).

**Touch by standing on top.** The hero's z base `D2` is compared with each object's top z. When they are equal (the hero is standing on the object) the scan reaches `$008a02` and queues event 9 for it (`$008a26`, `$008a5a`) every frame. This is how landing on a gem or an altar fires touches that a walk beside it cannot, and why the TUNNEL lever, whose only reachable overlap was from above, answered nothing when stood on: it has no event-9 block.

**Jumping.** FIRE with nothing directly in front is a jump. The hero rises while the button is held to a bottom z of about 35 (34 above a stand at z 1, 35 above a floor mark, whose top z 1 makes the stand z 2), then falls. Measured: lift-off about 80,000 steps after the press, bottom z 22 by 192,000, apex 35 at about 320,000 and back to 22 at 448,000; the takeoff direction fixes the arc and a direction added later changes nothing; horizontal travel is one cell per 25,000 steps for the whole arc (13 cells for a 300,000-step hold). A takeoff adjacent to the target wall does nothing and a run-up of 8 or more cells works; an object overlapping the hero's x and y whose bottom is above stops the rise at that bottom (the caps of room 89). A jump lands on any top at z 22 or lower, which is how the hero reaches the items resting on the two altars of level 0 (z 22 to 25); walking off an altar top is free. The hero cannot shoot or cast in the air: the fire read at `$006e10` runs only while the jump pointer `312(A5)` is 0, and a fire held across a flight acts at landing.

**Solidity summary** (level 1 drive): blocks, pillars, hounds and flyers block when their z range meets the hero's; the portal of a door is entered only when the whole bounding box lies inside its range (the lane is the hero's lead coordinate); a room change is refused, and the hero put back, when the arrival rectangle overlaps an object (room 30's door `$2f` with the trap 635 shown; `BOTH ROOMS BLOCKED` is the debug string of that check, *inferred*). The front test that the FIRE probe uses is one step ahead along the facing vector and includes z, so an item that is no obstacle is seen only from directly beside it.

## 4. Doors and room changes

**The portal table.** A second table in the same format as the object array: `(A5)+88` (the buffer `$037e48`, reused by every room), count `(A5)+1162`, stride `$46`. `$008ac8` consults it only for kind 7 (the hero); any other mover reaching the edge is left alone. Each entry is a **threshold test, not a box**: `byte0`/`byte2` and `byte1`/`byte3` are independent lines that the footprint must straddle in the direction of travel (so `byte0 > byte2` is normal), and a diagonal-corner allowance keyed on the joystick latch (`btst #0/#1,2243(A5)`) lets the hero graze a doorpost. A match returns `D0 = -2`, `D1 = entry.+10` (the door descriptor) and stores `entry.+26` in `(A5)+1184`, the pending room target (idle `$ffff`); no match is a hard wall (`D0 = $FF`). The executor runs on a match. Live tables:

```
TUNNEL entry 0 @ $037e48  bbox [1b 2d 04 28]  descriptor $06d4ea  +26 = $0032   (south edge, the CAVERN link)
TUNNEL entry 1 @ $037e8e  bbox [1b 05 04 00]  descriptor $06d4f2  +26 = $0033   (north edge: the lever's door)
CAVERN entry 0            the same descriptor $06d4ea, +26 = $0032
CAVERN entry 1            descriptor $06d532 (id word 73), +26 = $003b            (east wall, x line 80)
```

**The door descriptor** is an 8-byte type-4 record (`py/door_walk.py` resolves door id to record through the type-4 row: `$32` to `$6d4ea`, `$33` to `$6d4f2`, `$3b` to `$6d532`):

| byte | meaning |
|---|---|
| `+0`, `+1` | the candidate world coordinate `(cx, cy)` the crossing lands on |
| `+2..+3` | the id word, the door's lock (below) |
| `+4` | bit 0 picks between two `$0158f8` calls at `$007280` (sound, *read*) |
| `+5` | the arrival facing, copied to `2275(A5)` |
| `+7` | bit 1: the key is consumed; bit 2 alone: the word is cleared and the key kept; neither: the item must be carried at every crossing; bit 3 is set after a crossing (`$0072bc`); bit 5 clear lets the UNLOCK DOOR spell open the door (*read*); bit 6 gates the sound push of a shut door at `$00731e` |

**The id word has three states.** `0` is open, `$ffff` is shut to everything but a script (the crossing only plays a sound cue: `$00731e` pushes ring op `$30` payload 8, then `$3c` through `$0158f8`, and commits nothing), and **a positive value is an item id: the door is a lock the rucksack opens.** The reader is the door branch `$00716e`-`$0071bc` (read, with the iron-key crossing driven): for a positive word it scans the rucksack (`jsr $011256`, a linear scan of the type-8 list, key `D2`), and if the item is found it applies `+7` (consume with `$00c3d4`/`$00e4fa` and clear the word, clear and keep, or leave), plays sound `$12` and falls into the resolver; if it is not found the crossing is dropped at `$00734a` with no sound and no room change. Driven natural: CAVERN's east door at x lead 79 stalls without the iron key (word stays `$0049`), crosses into room 8 with it (word `$0049` to `$0000`, rucksack 1 to 0). Scripts write the word with verb 10 (CLEAR FLAG, operand a hex door number) and verb 27 (SET FLAG); these and `$0071b8` are its only writers in the main image and the overlay. The lever of TUNNEL clears `$33`: operating it from its panel (icon 7, event 5) rewrites the descriptor `14 0b ff ff 01 01 00 00` to `14 0b 00 00 01 01 00 00`, after which Up leaves TUNNEL for room 2 (the control run without the panel stays put). In level 0, 13 doors start `$ffff` (`$09 $12 $18 $1c $22 $23 $24 $25 $26 $29 $33 $3f $40`), 5 are keyed (table in section 11) and every one of the 13 has an opener.

**The destination is found by position, not by the id word.** After the lock test, `$0071ca` computes the arrival from the descriptor (`+0`, `+1`, facing `+5`) and `$00de5e` scans the type-3 table: for slot 0, 1, 2 ... up to the table's bound it builds the rectangle `x0 = +1`, `y0 = +3`, `width = +4`, `height = +5` from the room record and tests `x0 <= x <= x0 + width`, `y0 <= y <= y0 + height` (inclusive), returning the first slot that contains `(cx, cy)`; none gives the `DOOR ERROR` debug message. The door `$32`'s coordinate is `(20,17)`, the shared edge of TUNNEL (`[19,12]-[22,17]`) and CAVERN (`[12,18]-[22,28]`); the first `$de5e` call during the crossing tests slot 0 and fails, slot 1 matches (`bpc $de5e`, `D0 = $14`, `D1 = $11`). Over all 72 rooms, 71 distinct door ids are referenced and every one resolves to the door's own room or an edge-adjacent neighbour (`door_walk.py`): there are no teleport doors in the door data, and a door's id word never selects the destination.

**The commit** (`$007250`, *read*; observed at the TUNNEL to CAVERN crossing): `D0`/`D1` come from the descriptor and `jsr $de5e` resolves them to `D7`; a negative `D7` takes the no-door path. When `D7` differs from the current room (`cmp.w 1166(A5),D7`) the pair is exchanged (`exg D6,D7`) so that the resolved slot is committed, otherwise the value in `D6` from the arrival-point resolution at `$0071ca` is. `move.w D6,1166(A5)` at `$00727c` makes it the current room; in the live TUNNEL to CAVERN crossing `bpc $727c` shows `D6 = 0` (CAVERN) with `D0 = $14`, `D1 = $11`. The block then calls `$00e854` (room activation, section 5), sets `bset #3,7(A0)` and branches to `$0069da`, the main-loop re-entry (a frame sync `jsr $011898` followed by per-frame housekeeping; there is no copy or unpack step in it). A name banner may be queued first: `$007310` writes the message index 2 into `2142(A5)`, the gate `addi.b #2,D4; bpl $0069da` decides whether `bsr $defa` pushes ring op 8 (section 7). `$00e84a` is `move.b #$ff,2271(A5); bra $00e854`, the same routine entered with the block flag forced.

**Driving the CAVERN to TUNNEL crossing.** From the CAVERN start the route is Right 1.2M steps, Up 0.5M, Right 1.2M, Up 1.2M on joystick port 1 (the first Right leg picks up a SILVER COIN on the way); the door `$32` fires and TUNNEL's entry is `[20,12,14,6]`. The reverse crossing is Down from that entry (`kbd ff 02`, about 2.2M steps; Right and Up from the entry are blocked at once). The same zigzag crosses in the two-disk build (Right 1.2M stalls at `[69,23,63,17]`, Up 500,000 steps crosses and `164(A5)` goes from `$6c00a` to `$6c072`).

**Teleports and the level start.** A script moves the hero to a room no door joins with verb 37 (`room x y z`, `$010974`): it writes the room byte into `1166(A5)`, resolves it through type 3, reads three more bytes (x, y, z in cell units: the bounding box is 8 times them) into `2134`, `2136`, `2138(A5)`, calls `$00e854` and branches on its success. The overlay reaches it as export service 8 (`secrets.md`, "The level code overlay"). Room scripts teleport on region events (event 15 for the hero), and the level-start code `$0069ba` converts the maximum health `2516(A5)` to two thirds (`divu #3`), stores it in `1174(A5)` and activates room 0 (read). The graph of verb-37 edges, with the room pairs they join, is in sections 11 and 12; door-only reachability in level 0 with every `$ffff` door opened and every key held is 65 of 72 rooms (not 27, 28, 29, 37, 47, 69, 71), and with the verb-37 edges 70 of 72 (not 69, 71).

**What the door data cannot do.** No instruction of the loaded image reads a disk (section 1), so rooms 27 to 29, level changes and the like are scripts, not loads. A level change is verb 51 (START LEVEL, `secrets.md`), which shows the "PLACE LEVELS DISK" prompt, waits for a key and runs the expander and raw reads again (four expander calls and five raw reads in `hits`); the one-disk image holds two populated levels (directory at sector 400), the Level disk of the two-disk build five.

## 5. Room activation and the screen

**Activation** is `$00e854`. Its only input is `1166(A5)`, the target slot: it sets `164(A5)` itself (the write at `$00e95c`; the boot call `$00e80c` activates slot 0), then runs `$00e7b0`, `$00ccd4` and the frame bookkeeping. Callers: the door commit `$0072ac`, the level start `$0069ba`, the teleport verb `$0109ca`/`$010a58`, and the boot. `callcap e854` with only `1166(A5)` written to a slot loads that room's objects (the REPL writes it as `w 185e0 <(slot << 16) | $2888>`: `w` writes a longword and `1166(A5)` is a word, so the neighbouring low word `$2888` is kept; run for all 72 slots: 56 instantiate exactly the type-5 list in order, and 14 rooms with 35 objects write fewer entries than their list, through a second path of the loader at `$00cdc2`/`$00cde6`/`$00cdf0` that is not read; `py/full_room_name_census.py`). Writing `164(A5)` alone repaints nothing; a hand replay of the diffs of `$e854`, `$e7b0` and `$ccd4` changes the object state but not the screen.

**The tile offset table** (`$00e7b0`). It reads the new room record's `+4` and `+5` (width W, height H), forms the index `(W - 3) * 2 + (H - 3) * 16` into the word table at `$5a10`, stores the word in `148(A5)` (TUNNEL 3 by 5 gives index `$20` and `$2d50`, CAVERN 10 by 10 gives `$7e` and `$1268`), and builds a row-major table at `2634(A5)` with stride W:

```
screen_offset(row, col) = base + row * $4f8 + col * $508        row < H, col < W
```

(`$508` is 8 scanlines plus 16 pixels to the right and `$4f8` is 8 scanlines minus 16 pixels, the two diagonal steps of the isometric view; 15 of 15 cells of TUNNEL and 100 of 100 of CAVERN check). The consumers are `$00d09a` (a row stride of W + 1 into the table at `84(A5)`) and `$00d06a` (the per-object screen position: `A2 = 2634(A5) + word[2634(A5) + D1*2]`, adjusted by `+4` again). How the terrain tiles are chosen and drawn through this table is `graphics.md` section 5; the tile stack unpacker is `secrets.md`, "Loading, the expander and the level directory".

**The object array is rebuilt** by `$00ccd4`: it clears the buffer at `68(A5)` and re-initialises the 70-byte entries of `(A5)+56` (95 slots) with sentinels (`$00ccfe`), then `$00cd50` reads the room record. It zeroes `1148`, `1150` and `1152(A5)`, fetches the **type-5 list for slot `1166(A5)`** (one big-endian word per object: a type-6 object id; `+29` of the room record says how many) and instantiates each: `$c5a8` with `D0 = 6` returns the template, a 70-byte entry is filled from it, `1152(A5)` is incremented by `$00ce2e` once per object (about 115 steps apart, 22 times for CAVERN), the entry's `+6` receives the **live instance record** (`move.l A0,6(A1)` at `$00ce78`) and its `+10` the type-6 record, and the template's word `+8` receives the entry's byte offset in the array (`$00ce5c`), valid only while the object is instantiated in the room that is loaded. Records are shared: rooms reuse decoration records (the SCONCE record `$5f864` serves 10 rooms). The array is only the **props**, not the terrain: no object of CAVERN's 22 is wall scale.

**Three buffers carry the picture.**

- `(A5)` and `(A5) + $7d00` (`$19100` and `$20f00`) are the two halves of one 64,000-byte display double buffer. `(A5)+0` always points at the half that is **not** on the screen; the shifter shows the other (`$20f00` against `$19100` in 5 of 7 snapshots; the other 2, taken mid-flip, are *inferred* to be the same invariant a flip apart). Nothing during a crossing or 8.2M idle steps reprograms the shifter: `$015272` (`movep.w D0,0(A0)` to `$ff8201` from `(A5)+0`, one of 14 sites that name the register) never runs, and `watch` does see `movep` writes.
- `120(A5)` (`$2de08`) is a third, resident 32,000-byte buffer. `$0144b8` (`ScreenFlip_ScanlineCopy`) refreshes a display half from it: it reads forward with `movem.l (A0)+,#$fcff` and writes backward with `movem.l #$ff3f,-(A1)` in 56-byte chunks (142 pairs per outer iteration, 4 iterations, 3 more pairs, so 571 chunks, plus one 24-byte chunk before or after them depending on `$5a99`), yielding to the VBL through a vector installed at `$90`. Each chunk keeps its internal byte order and the chunks land in reverse order, so `120(A5)` is the same 320 by 200 four-plane raster stored with its chunk order reversed. `py/decode_backbuffer.py <snap>` decodes it (0 of 32,000 bytes differ from `(A5)+0` in `room2_tunnel_entry.snap`, the only snapshot taken between the flip and the later sprite and panel passes).
- The same routine runs with source and destination exchanged, from the wrapper `$00bba8`: at a crossing it **banks the inactive half back into `120(A5)`** (`A0 = $20f00`, `A1 = $35b08 = 120(A5) + $7d00`). `120(A5)` is therefore a cache of whatever was last composited into the display, which the ordinary per-frame flip uses to refresh a half cheaply, not the room's source art. `$00bba8` runs 4 times in a crossing and never in idle play; `$5a99` is local scratch of the wrapper (it toggles within about 1,200 steps of every call) and is not a "crossing done" flag. Use `1166(A5)` for that.

**A crossing, seen from outside.** No trap and no FDC command is issued (`ATARI_TRACE_OS=1` and `ATARI_TRACE_FDC=1` over 2.5M steps: zero lines), `120(A5)` changes from TUNNEL to CAVERN art, and the room is repainted by a burst of the shared masked blit `$0150b4` (4,066 calls between step 49,322 and 1,058,685 of an 8.2M-step crossing, none in 8.2M idle steps) driven by the visible-object walker `$00d800`-`$00da06`, the same per-frame walker that draws moving sprites; both display halves match the target room's reference to 98% once the burst ends (656 and 636 of 32,000 bytes differ, the player sprite among them). A render taken right after a room change shows the old room for about 100,000 steps. The picture, the masked blitter and the depth order are in `graphics.md` sections 4 and 5.

**The panel redraw.** `$00014a90` (`$014b28` for its blit) repaints a fixed element at screen position (272,143) on every crossing: it ANDs the 12-word mask at `496(A5) + $c0` into the live screen at `(A5) + $59e8`, copies the first `$60` bytes of the structure at `496(A5)` over its `+$60`, masks that copy with a word pair taken from `$60fc` and indexed from `2516(A5)` through two divides (`2516(A5)` is the maximum health; what the pair draws was not read), and blits `$55b6` (96 bytes of zero: a cleared panel) with `$014d7a`, `D6 = 2`, `D7 = 6`. `A0 = $55b6` is the same in both crossing directions. It never runs for a same-room proximity change (zero hits over a full walk into the lever's hotspot with `bpc $014a90` armed).

## 6. Nearby objects, the status bar and the icon panel

Standing next to an object changes the status-bar name and the icon row without any special case: the **proximity test is the collision scan**. `$008870` builds the list of overlapping objects at `(A5)+92` (section 3), with a small margin around the candidate position. After every accepted step the handler `$007368`-`$0073da` computes the facing vector (`$0077fe`: the direction table indexed by `2273(A5)`, negated while `2340(A5)` is set) and, when `$008870` accepted the move, calls `$009440` with `A0 = 92(A5)`.

`$009440` walks the list: each entry resolves through `56(A5) -> +8(A6) -> +6(A4)` to the live record, and an object whose record has bit 6 of byte `12(A4)` set is skipped. For the first eligible object `$00946a` sets `456(A5) = $5ff6` (the icon table), compares the object's **name index** `10(A4)` with the name now displayed, `1222(A5)` (the status bar reads this field, so name and icon row are one write path), and appends icon bytes conditioned on the object's bits (bytes `12`, `15`, `22`, `23`, `29` of the record; one icon comes from the verb-to-icon table `$5c1c` keyed by byte `23`), always ending with icon 6 (cancel); the count goes to `2303(A5)`, capped at seven (`SEVEN OR OVER ICONS`). At TUNNEL's lever the table reads `07 0b 06` with count 3 (idle `ff ff ff`, count 1); the boat of CAVERN resolves through the same call site (return address `$00007376`) and the same list, entry `$0007061e`.

**The redraw is a diff.** `$00958e`, in the input dispatcher `$009542`-`$0095ea` (gated on `btst #1,2499(A5)`), calls `$00bbcc`/`$00bbd4`, which compares the table at `456(A5)` with a cached copy and calls `$00bca0` only for slots whose icon changed. `$00bca0` draws one glyph: `A0 = 332(A5) + icon * 112` (112 bytes = 32 by 14 pixels), `A1 = $5fbe + slot * 8` (fixed screen positions), `jsr $14d7a` with `D6 = 1`, `D7 = 14`, which lands in `$0150e2`, the same masked blit as everything else. For the lever the changed pixels are x 10 to 49, y 155 to 181.

**What the fire button does.** With an object directly ahead FIRE opens that object's panel (`secrets.md`, "The player's action panel": the icon loop `$009c82` first waits for FIRE to be released, a second press confirms the highlighted icon, and `$00a0ac` dispatches the returned icon id). A FIRE press also runs a rescan (*read*) of the object array (`$00afb2`, stride `$46`; `$00b1a2` asserts the animation pointer is even, `ANI PIC HAS GONE ODD`) that packages the nearest eligible object (`$00db4a`) and draws its selection box (`$00db8a`, via the queue at `(A5)+344` and the overlap-list builder `$00ddb6`). That chain writes nothing to the portal table, a door descriptor or any room global (watched across a tap, a release, the interact key, fire plus Left: zero hits, identical dumps): it is the highlight, not the action. `$00af6a` calls the glyph draw `$00bef0` with `2455(A5)` for objects whose struct byte `22` is 6 (another type with bit 5 of byte `12` set prints `UNKNOWN ANI OBJECT`); `2455(A5)` is the hero's **walk animation frame byte**, written only at `$0075d8` from a byte stream whose pointer `(A5)+376` `$007480`-`$007536` picks among six tables (`$5c46`, `$5c79`, `$5cac`, `$5cc3`, `$5ce6`, `$5d09`) by the move state `2266(A5)` and direction fields; it is not a UI cursor.

**Mouse.** The game sends only three IKBD commands from boot to gameplay (`$80 $01` reset, `$12` mouse off, `$1A` joystick auto-report off): `$07`, which would enable buttons-as-keys, is never sent, and a live `mouse down l` reports `buttons-as-keys=false`. Mouse clicks do nothing in play; every action comes from the joystick (port 1: `kbd ff 01/02/04/08` for up, down, left, right, `kbd ff 00` to release) and the keyboard.

## 7. The event queue and its consumer

Everything that happens in a room because of something the hero or the world did goes through one ring queue at `(A5)+304`, count `1154(A5)`. Every producer is followed by `cmpi.w #$c8,1154(A5)`, so the ring holds 200 entries; whether a caller tests the flags that compare leaves, and so whether the ring can overflow, is unread.

**Entry.** Three words: the opcode word, a longword payload (a record pointer), and a third word that the consumer stores in `1156(A5)`. The low byte of the opcode is the **event number**. Bit 15 makes the entry 12 bytes: the consumer reads a fourth longword and stores it in `384(A5)` (the 8-byte form leaves `384(A5)` stale, and the gate copies the stale value). Bit 14 says the payload is a **room record** rather than an object: the consumer then looks in the room's own block list (`+$20` of its structure, count at `+31`) instead of the object's (`+$10`, count at `+11`). All eight room-addressed pushes (events 6, 14, 15, 17, 19, 20, 24 and 28) load `164(A5)` or a room from it; bit 14 never selects a second object list (the "list at `+$20`" of object 3 in level 1 is the next record's first list, because object 3 is a 16-byte header-only record: 315 blocks walked and 313 distinct addresses in level 0, 442 and 440 in level 1). Bits 8 to 13 would index the gate table past its end and no producer sets them.

**The consumer** is `$00fdbc` (`Ring304QueueConsumer_DispatchByOpcodeByte`), the only code that decrements `1154(A5)` (`subq.w #1,1154(A5)` at `$00fe74`). Event 8 is tested first with a byte compare, before bit 14 is looked at, and goes straight to `$00ffa4` (the name banner, below). Every other event walks the owner's script blocks, `[tag][length][payload...]` records (`$00fe0c`-`$00fe70`, bounded by the count in `1168(A5)`), comparing each tag with the opcode's low byte; a match calls the gate dispatcher `$011728` with the gate table at `$00fe84`, and a block whose gate accepts runs its verbs through the verb table at `$00ffba` (consumer entry `$00fe54`). The gates, the verb vocabulary and the block format are `secrets.md` ("How the script system fits together", "The script language", "Gate bytes"); section 9 records what was measured.

**Timers** share the ring: `TimerQueueService` (`$009006`) is a producer (it pushes `$400e` and `$4014` itself) and drives a table of up to 16 countdown timers at `2534(A5)`; one timer tick is 17 calls of it, about 410,000 steps.

**Opcode 8, the name banner.** `$defa` pushes `[8][message index from 2142(A5)]`, and `$00ffa4` draws it: it selects the inactive buffer (`$011338`), and `$00a836` (`NameBanner_DecodeStringAndUpdateSlotCache_ByD0Index`) decodes the string (section 8), looks it up in a 4-slot least-recently-used cache of 10-byte slots at the fixed address `$6000`, word-wraps it (`$00e030` with `$0116dc` for character widths) and draws the box from the template at `$5c00` (`$00bcd0`, helpers `$00bd6e`, `$00bd92`, `$00bd98`). `2142(A5)` is a general message-index register that the game writes with some two dozen different literals from over a dozen routines before asking for a banner (`$2` at the door site `$007310`, then `$3`, `$e`, `$f`, `$1b` and on up to `$35`); it is not a room-load flag, and `$defa` never reaches the disk. (The icon panel's diff cache is also described at `$6000`; the two readings of that address are not reconciled, section 15.)

## 8. Names, creatures and the GIANT RAT

**The string table.** `(A5)+168` is a word-indexed offset table and `(A5)+172` the base it is added to; the stream is 6-bit packed, four characters to three bytes (`b0>>2`, `(b0&3)<<4 | b1>>4`, `(b1&$f)<<2 | b2>>6`, `b2&$3f`) through the 256-byte character map at `$5ac0`, ended by a map entry of `$ff`, and decoded into a buffer at `3234(A5)` by `$00fd2c`/`$00fd4e`/`$00fda2` (23 callers: a general string fetch). `py/name_strings.py` decodes it with no input. Indices 0 to about 599 are readable; from there the table decodes to a repeating `DOOR` pattern and then zero padding (swept to 999), so there are no further names. An index decodes to its terminator, but a raw read of 224 runs on into 225 (`SCONCE`, `DEAD RAT`). The table holds the UI vocabulary, the spell list, item text, lore, the diary text and the hints. Anchors checked against the live status bar: 200 `LEVER`, 188 `BOAT`, 197 `PICKAXE`; the cluster 224 `SCONCE`, 225 `DEAD RAT`, 226 `GIANT RAT`, 227 `LID`, 228 `CHAIN`, 229 `FLAME`, 230 `PLANK`, 231 `CONOPTIC URN`, 232 `SKULL`, 233 `SKELETON`; 159 and 160 the WAKE and SLEEP messages (`THE CREATURE IS SLEEPING`, `THE CREATURE AWAKES AND IS VERY VERY ANGRY`); 272 three hints, including `MOST SKULLS WILL HELP YOU COMBAT THE SPINE CREATURE`.

**An object's displayed name** is not in its type-6 template. The chain, with `type6(id)` the template:

```
slot_off  = u16(template + 8)                 written by the room loader ($00ce5c); valid only while the room is loaded
slot_addr = u32((A5)+56) + slot_off
live_rec  = u32(slot_addr + 6)                written at $00ce78
name_idx  = u16(live_rec + 10)                the index into the string table
```

`py/room_object_names.py` implements it: TUNNEL's lever (object 144) gives 200, CAVERN's boat (257) 188 and its pickaxe (168) 197, validated on 23 of 23 objects (CAVERN's 22 and the lever, the lever by driving the room load from CAVERN's state). For an object of a room that is not loaded `template+8` reads 0 and silently aliases object 0's slot, so a census of an unloaded room returns another object's name; load the room first. The prop that `graphics.md` called a goblet (slot 16, object 413) is `SCONCE` (224). Live records are shared between rooms (SCONCE's serves 10).

**Creatures.** Type 9 (the creature instance table) is empty in every snapshot, and loading a room never writes it (`watch` over its index table and over `2120(A5)` across `callcap e854` for slot 27: zero hits). The creatures a room shows are objects of type 6 created by object and room event blocks: the hounds and flyers (ids from 900 up) by an entry block, spiders and maggots by touches and removals. The walkthrough's numbering is the slot plus one (room 1 is slot 0, CAVERN; room 2 is TUNNEL; room 3, slot 2, holds the bag of stones, id 23; room 19, slot 18, the KEYHOLE).

**The GIANT RAT is the one placed creature**: of the 56 rooms whose census was clean, only slot 27 carries a monster name (226), as object 194, live record `$0005d62a`, template `$00070034`. The other monster-cluster names appear 2 to 11 times each as shared scenery. Slot 27 is a 10 by 10 room with a 166-byte record: 6 stones, 5 bones, a skull (215), the rat, parchment, a key, a chest and 3 funghi. KILL, UNINV, WAKE and SLEEP all take their success paths when called with the positive id 194 (the resolver's type-6 branch, `callcap $010354`, `$01038a`, `$0103e0`, `$0103f8` with `A1` at the bytes `00 c2`: `A0 = $00070034` each time, KILL queueing its 6-byte record and incrementing `1154(A5)`); the downstream action of SLEEP (`$00e172`) does not return under `callcap`, very probably because it plays a cue and waits on a flag only an interrupt clears (`callcap` runs with interrupts masked). The same four verbs fail through the type-9 branch because that table is empty. Not examined: the 14 rooms of section 5, slot 69 (102 loader writes for 28 ids) and slot 71 (a type-5 list without its terminator).

## 13. The disk images and the two-disk build

The one-disk Empire `.st` (819,200 bytes) is a non-filesystem, self-booting disk: its root directory is 224 bytes of `$e5`, the boot sector (checksum `$1234`) loads track 79 and the loader reads the cracktro stage and the game image. The level directory, the expander `$0118ec` and the packed blocks are in `secrets.md` ("Loading, the expander and the level directory"); the one-disk image holds **two populated levels** (directory at sector 400), the Level disk of the two-disk build five. `py/disk_layout.py` classifies a sector as blank only by a single repeated byte, so it overstates Disk 2's real data (98.4% reported against 91.9% once the 3-byte filler of its tail is counted); its sector map is a layout aid, not a content test, and the entropy readings in `py/analyze_disk2.py` do not distinguish packed data from random: every level block is packed, which is why no tile or sprite structure shows in the raw bytes.

**Which image to use.** The two-disk original comes in cracks of different groups and dumps: the Empire `[t]` Disk 1 runs a scrolling greet-list and a loading-bar screen that loops (about 100 times the steps the one-disk release needs to reach gameplay; no key, space, return or `1` broke it within a 5M-step window), the Replicants/ST Amigos Disk 1 parks at a trainer screen, then the title, a language select (`1 ENGLISH / 2 FRANCAIS / 3 DEUTSCH`), the restore prompt (ESC starts fresh) and `PLACE LEVELS DISK IN DRIVE ONE AND PRESS A KEY`, in under 100M steps; `.stx` (Pasti) dumps are not raw sector images and this emulator's loader has no format check, so a `.stx` is read as garbage sectors without an error. Replicants' Disk 2 and Empire `[t]`'s Disk 2 carry the same payload (98.3% of 4-byte-aligned bytes identical) but the Empire dump is damaged in levels 3 and 5 (`secrets.md`); use the Replicants one.

**Driving the swap.** A snapshot does not hold the disk in drive A (`MMU.LoadDiskA` is excluded from the snapshot on purpose), so every `resume` starts with no disk, and every FDC read then returns "no data" for any track and sector: that looks exactly like a missing sector. Mount the disk with the REPL's `disk <path>` after every snapshot load; the REPL splits on whitespace with no quoting, so copy a file with spaces in its name to an unspaced name first. Disk 2's boot-sector BPB declares one side while the file is a double-sided 819,200-byte dump, and the loader once believed the header (every side-1 read returned "no data" and the game reported `THERE SEEMS TO BE AN ERROR ON THIS DISK`); `LoadDiskA` now prefers 2 sides when the file is large enough (commit `5547ae9`). Disk 2 is never booted (the swap happens in a running game and nothing executes its boot sector, which holds only the signature and the BPB).

**The protection after the swap** is Rob Northen's CPU-detection and self-decrypt chain, reached by `jsr (A2)` at `$00011602` from the embedded-resource-stream dispatcher `$011598` (descriptor triples `{base, length, pos}` at `(A5)+2538`; `A1 = 0` means execute the chunk in place) into `$00021da0`. It installs its own illegal-instruction handler at vector 4 and deliberately executes reserved opcodes: `MOVEC` (`$4e7a`/`$4e7b`, already an `Illegal` pattern) and a MOVEQ encoding with bit 8 set (`$712c`), then sets the trace bit and uses the trace exception (vector 9) as a single-step decrypt loop. The emulator crashed on the reserved MOVEQ and never took the trace exception; both are fixed (`ReservedMoveq`, commit `1cb269b`; trace mode sampled before each instruction and `EnterVector`/`EnterGroup0Vector` clearing T1, commit `1f41114`, each with the regression net's proof). Past them the crack reads Disk 2 normally.

**What Disk 2 contributes is a one-time load.** With Disk 2 mounted the boot to gameplay performs 121 sector reads in the first 30M steps (ending at track 13 side 1) and none in the next 60M steps or across a CAVERN to TUNNEL crossing (`ATARI_TRACE_FDC=1`); the screen reaches `DAY 1 / BOAT / CAVERN` at 90M steps (`PC = $00015254`). The type-3 room table, the door table and the rendered art of CAVERN and TUNNEL are identical to the one-disk build's (72 rooms, byte-identical rectangles, a pixel diff of 1,552 of 64,000 pixels in TUNNEL that is the hero at another position). The structures sit `$100` bytes higher (section conventions): the player entry is at `$038438` and a hand-check at `$038338` reads a stale, plausible-looking box that does not move.

## 14. Traps in the evidence

These are the ways the investigation of this file was misled; each is a check to run before believing a claim of the same shape.

- **A negative search is bounded by its technique.** A static call-site scan (`find_ram_callers.py`) cannot see an indirect call, `find_literal_ptr.py` cannot see a displacement table, and `find_jump_table_hit.py` sees only tables whose base is a literal in the image. The thread that chased "what calls LOCK on object 144" through four static techniques and an 18-site sweep found nothing because the table it was looking for was the tail of a larger one (section 9) and the real caller, the consumer `$00fdbc`, indexes it by a base the scans did not model. Check a table's base and size against the code that indexes it before attributing ids, and treat a table whose first word is its own byte count as a size field.
- **`callcap` proves an effect, not a caller.** It reverts memory after reporting its diff and runs with interrupts masked, so `callcap $01049a` flipping a lock bit says the verb works, not that anything invokes it, and a routine that plays a sound waits forever on a flag only an interrupt clears. To hold a flag set, poke it with a real `w`; `w` writes a longword (an odd address is an address error), so a one-byte field is written through its aligned longword with the three neighbours preserved. A flag held set for 5,000,000 steps with nothing reacting rules out background polling, which `callcap` cannot.
- **A position, an approach and a settle.** "Blocked everywhere" was a short step budget (section conventions); "the hero is one unit short of the lever" was real (the lever's box is reachable only from above) but not the mechanism; a hotspot found at one tile may not exist at the next. Vary one thing between trials and keep a same-snapshot control.
- **Addresses are per build, and per room.** Resolve `(A5)+96`, `(A5)+56` and `(A5)+164` from each snapshot (the two-disk build moves them `$100`); a template's `+8` is valid only in the room that is loaded; a type-6 record's address is not stable (a DELETE compacts the heap: `H.obj()` in `verbs2/h.py` reads the snapshot file and goes stale, and the lever 719 moved down 16 bytes when a 16-byte gem was deleted: resolve through the live index entry); a poked type-8 record needs its index entry (`[size 4][offset 4]` at `idx + 4*slot`) because `$00c628` walks the index, not the count `2438(A5)`.
- **Readings of a constant can be right and mean something else.** `2516(A5)` looked like a day or variant counter and is the maximum health (the day is `2166(A5)`); `$5a99` looked like "crossing done" and is scratch; `(A5)+1166` is the current room and `164(A5)` the pointer to its record; `(A5)+0` is the half of the display double buffer that is not on the screen. A field named from where it is seen running is a hypothesis until its writer and reader are both read.
- **A render or a diff may show the old state.** A render within about 100,000 steps of a room change shows the old room; restrict a pixel diff to the region of interest (a whole-frame diff of two lever states returned a 280 by 125 box because the hero had moved). A probe (`Q` in `explore.py`, a FIRE with nothing in front) leaves the hero airborne, so never save a snapshot to start a chain from right after one. Health alone does not show a poison bite: read `2434(A5)`.
- **`slot_map()` in `g2/lib.py` starts at slot 1** and skips the first rucksack item (read `type8(r)['recs']`); `lib/drv.py` does `os.chdir(ROOT)` on import (absolutize snapshot arguments). Two lineage snapshots sit in the `$0117c4` fatal-assert spin and cannot run (`s86/a7/snaps/gomove31.snap`, `s86/a6/snaps/room69.snap`); verb 41 PLACE with no free space asserts and hangs the game.
- **Injected states show a mechanism, not a route.** Label them; health goes up only by a verb 45; door words are hex door numbers; the REPL prints at most 4,096 lines.
