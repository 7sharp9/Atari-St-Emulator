How Crude Buster decides who gets hit

The game never compares sprites. Every punch, bite and explosion is a rectangle test, and every enemy that does more than walk straight at you runs one shared decision routine. Both are small enough to read in full.

Crude Buster (Two Crude in the USA) is a 1990 Data East arcade fighting game for one or two players. The attract screens set it in NEW YORK A.D.2010. You walk right through six levels (numbered 0 to 5 here, as the program numbers them) and fight the thugs, cyborgs and bosses that a level script releases as the screen scrolls. There are three buttons: attack, jump, and grab or throw, which picks up props and enemies and throws them. This page answers two questions a programmer would ask about such a game: how does the program decide that a blow connected, and how does an enemy decide what to do next?

The answers are cheap. A hit is four integer comparisons between two rectangles. An enemy's next move is three table lookups, by height, by distance and by what you are doing, followed by a random choice among a short list of next states. The surprising parts are in the details: an enemy that touches you loses health as well, you are not protected for even a frame after a hit, and the same enemy behaves differently depending on whether you stand on its level or above it.

Setup. Crude Buster is an arcade board, not an Atari ST game. It runs in MAME 0.289 (set cbuster, the World version), which here serves both as the emulator and as the reference for what really happens. The board's main processor is a 68000, the same CPU family as the ST, so the repo's disassembler reads its program. The program is stored encrypted in the ROM chips and MAME decrypts it as it loads; every address on this page (written like $2438a) is an address in that decrypted image. Addresses are citations only: the prose says what each one does.

Before you read

Terms used on this page

frame
One step of the game's logic. The game advances once per video frame, 58 times a second in play. Durations and move timings are in frames.
pixels, x and y
Game pixels in the level's own coordinates. x grows to the right, y grows downward, so "above" means a smaller y. Numbers written $20 are hexadecimal: $10 is 16, $20 is 32, $100 is 256.
record, type, state
Each enemy is a 64-byte record in RAM holding its position, health, a type number (which enemy it is) and a state number (what it is doing now: idle, walking, attacking, stunned). The game keeps up to 16 enemy records; the level script keeps at most five of its enemies alive at once.
health
A byte in the record. You start a life with 56 (seven bar cells of 8). Most enemies have a few points; the bosses have 16 to 48.
box: R, L, B, T
A rectangle stored as four numbers: right edge, left edge, bottom edge, top edge. The ROM stores boxes as offsets from a fighter's position; the game adds the position each frame.
enemy names
The game prints no enemy names. "Bruiser", "Strongman" and the rest describe the sprites.

How sure we are

measured
Run in MAME and counted. "397 tests, 71 hits, 0 disagreements" means a script predicted the outcome of 397 cases from the rule and compared each with what the game did.
read
Read from the disassembled program, not run.
decoded
Computed by a script that reads the ROM tables and the code that uses them, without sampling the game. Exact if the reading is right, but not yet confirmed by counting in a run.
open
Not settled.
gate
A script that re-runs a check from scratch and reports matches out of cases, such as player/py/hitbox_gate.py. The script names in the source line at the foot of the page are the gates behind the counts.
lab, natural run
A lab run loads a saved MAME state, places chosen enemies and keeps the player alive, to isolate one mechanism. A natural run plays a level from its start with real button presses (see the last section).

Every fight is rectangles

Each frame the game takes the player's attack box and tests it against the body box of every live enemy, looked up by enemy type and state. A box is four numbers, right, left, bottom and top, and the whole test is four comparisons. The frames below are real, captured from MAME with the boxes read out of RAM and the ROM tables.

  1. The player's boxes. Every frame the player's code writes two boxes into the player's record: a body box (where the player can be hit) and an attack box. The attack box exists only while an attack flag is set, and that flag is set only on certain frames of an attack animation. A jab that is still winding up has no attack box at all.
  2. The enemy's body box. An enemy's body box comes from a ROM table indexed by its type and its current state, then shifted by its position. A stunned or falling enemy can have a different box from a walking one.
  3. The test. For each live enemy, the four comparisons in the grey box below. If all four hold, the enemy is marked as hit for this frame.
  4. The consequence. When the enemy's own code runs, a marked enemy loses 1 health and goes into a 15-frame stun; at 0 health it goes into its death state instead. A spark is spawned at the point of contact and the score is paid to whichever player landed the blow.
How to read the two frames. These are MAME screenshots enlarged four times, with the game's own boxes drawn over them by overlay.py. Green is the player's body box, yellow the player's attack box, blue an enemy's body box, red an enemy whose box the attack box overlaps on this frame. Nothing is drawn by eye: the corners are the numbers the game holds in RAM, converted to screen pixels with the game's scroll position.

Below is the test as the game writes it, with X the enemy's body box and Y the player's attack box, then the numbers of the first frame worked through. Each line reads as one condition: the attack's right edge is at or past the body's left edge, the attack's left edge is before the body's right edge, and the same two checks vertically. The mix of "at or past" (≥) and "strictly before" (<) means that boxes which only touch along one edge count as overlapping on one side and not on the other; it is the game's rule, not a rounding choice of ours.

hit(enemy body X, player attack Y) =
RY ≥ LX  and  LY < RX  and  BY ≥ TX  and  TY < BX
frame 1342, thug on the left: 612 ≥ 577, 580 < 592, 464 ≥ 432, 432 < 479, all true, hit
frame 1342, thug behind: 580 < 569 is false, no hit

Takeaway. The same comparison serves every kind of contact: your blows on enemies, enemies' blows on you, bodies touching, projectiles, and the grab's pick-up test. The program holds six copies of it, all equal; only the pair of boxes changes.

  • measuredIn a recorded fight against 40 grunts, 397 tests ran with the attack flag set. The box model predicted 71 hits; all 71 happened, and none happened that it did not predict.
  • measuredEnemy attacks use the same rectangles the other way round: a one-frame hit object is built from the attacker's animation, tested against your body box, then erased. 2,628 melee tests, 13 hits, 0 disagreements.
  • measuredA hit costs the enemy 1 health. The attack box is only live on certain animation frames, so a jab that is still winding up hits nothing.
  • readThe player's body box is 15 px wide and 63 tall standing, shorter when crouching or rolling, and empty (nothing can hit it) while being knocked down.
  • measuredBodies touching is a trade. When an enemy's body box overlaps yours, you lose 1 health and so does the enemy, and you are paid the points for hitting it. A thug with 2 health died from two touches without being attacked.
  • measuredYour punches never hurt the other player: there is no player-against-player attack path. In a lab test a three-hit chain over the partner's body box left the partner's health unchanged.

What each move reaches

The same body box and ground line in every cell, so the boxes compare directly. All move boxes are measured from the live player record and match the ROM table. The jab chain extends only if the next press arrives in frames 2 to 11 of the current jab.

How to read this. Each cell is one move for a player facing right, drawn at twice game scale. The green box is the standing body box, centred on the player's position; the dashed line is the ground under the feet. The yellow box is where that move can hit. Under each cell, reach is how far the box's front edge lies in front of the player's position, in pixels, and height is the box's height. The frame range is when the box is live, counted from the first frame the game sees the button (at 58 frames a second, frames 6 to 11 is about a tenth of a second). Units are game pixels, y grows downward. The jump kick box hangs below the body box centre line, so it reaches enemies lower than the player and cannot hit one standing on the same ground at head height.

Takeaway. Almost every blow reaches 40 px in front of your centre, so the moves differ mainly in height and in timing. The chain is three jabs: a second press within the window turns a 12-frame jab into a 24-frame two-hit move and a third press into a 42-frame three-hit move; each hit costs the enemy 1 health. Button priority is fixed: if several buttons go down on the same frame, attack beats grab and grab beats jump.

How an enemy decides

Thirty-odd enemy types, most of the bosses among them, call one shared routine at the end of their idle and walking states (`$2438a`, 40 call sites). It copies the position of a target player, then makes three lookups. First the height difference picks one of three tables. Beyond 256 px it simply walks in. Otherwise the distance, in sixteen buckets of 16 px, picks a row, and in the same lane the target's current pose and its variant pick the leaf. The leaf waits for the current animation to end, then rolls a die over a list of next states.

  1. Pick a target. With two players in the game, the enemy chooses one of them at random, skipping a player who is not playing or is knocked down, and copies that player's position and pose into its own record.
  2. Pick a table by height. Table A when the enemy stands between 32 px above and 96 px below you (roughly your level), table B when it is more than 96 px below you, table C when it is higher up. It also turns to face you, with 16 px of slack (48 px in tables B and C) so it does not flicker between directions.
  3. Too far away: walk. At 256 px or more horizontally the answer is always "walk toward the target".
  4. Pick a row by distance. Otherwise the horizontal distance divided by 16 gives one of sixteen rows of the enemy type's table.
  5. On your level, look at what you are doing. In table A the row is indexed again by your pose and its variant. Standing still is pose 0, variant 0, and a jab keeps pose 0 with variant 1 or 2, so the enemy can react differently to a jab than to standing still. The result is a leaf: a few instructions that end in a choice of next state.
  6. Choose. A leaf either sets the next state at once, or waits until the enemy's current animation has finished and then picks one entry from a list of next states with a random number, each entry with equal chance. The random generator is reseeded with the same value at the start of every level.
How to read the diagram below. You are the box on the left; the horizontal dashed line is your height. The three coloured bands are the three tables: an enemy whose y falls in a band uses that table. The ruler along the bottom is the horizontal distance between you and the enemy, cut into the sixteen 16-pixel buckets ($10 = 16 px); past $100 = 256 px the enemy only walks.

Takeaway. The personality of an enemy type is just its table. Distance decides most of it: close in, they mostly idle or attack; at middle range most of them walk in; far out, the jet-pack cyborg attacks and the armoured cyborg turns to its special states half the time. Height decides the rest: off your level, three of the four types below never attack and only try to reach your level. For these four types every real choice waits for the current animation to end, so an enemy commits to what it is doing before it reconsiders; only a cell with a single outcome, such as "walk in", fires at once.

  • decodedBruiser (8 health) within 32 px of you idles half the time, tries a grab a quarter of the time and uses its shuffling attack the other quarter. The grab squeezes you for 4 health each time.
  • decodedArmoured cyborg idles half the time and uses two attacks within 48 px, walks in at 64 to 127 px, and from 128 px out spends half its decisions on four different jump and special states, 12% each.
  • decodedStrongman has no attack beyond 96 px; past that distance it always walks. (At half health it becomes a different type that throws knives, which this table does not cover.)
  • decodedJet-pack cyborg is the only one of the four that attacks from range: from 64 px outward every decision is an attack, and from another height 38% to 56% of its decisions still are.
  • decodedOn another height the other three never attack. About 70% of their decisions walk toward you and the rest jump to your lane or drop to it first.
  • decodedThe grab attempt is conditional: it only becomes a grab if you are on the ground, not already held and not blinking. Otherwise the enemy idles.
  • open1,524 of the 1,536 table cells decode to exact probabilities. The other 12 (types 13 and 75, distances 64 to 159) use a leaf with a different shape. The rates have not yet been confirmed by spawning each type and counting its decisions.

What a hit costs

You start each life with 56 health. An enemy attack takes four times a table value that depends on the attack and on the difficulty switch. The 44 attack types on four difficulty settings:

How to read this. An enemy's attack is carried by a short-lived hit object, and each of its 44 types has one damage value per difficulty. Difficulty is a switch inside the arcade cabinet, set by the operator. Each row is one difficulty setting; each circle sits at a damage value along the horizontal axis, in health points. The dashed red line at 56 marks a full health bar: a circle on or past it is a single hit that ends a life from full health.
{{DAMAGE}}

The number in a circle counts the attack types that share that value; hover for their ids. The red circles are single hits that remove the whole health bar: attack type 32 on Hard (60) and Hardest (64). Hard and Hardest values are read from the ROM tables; the cabinet switch was not changed in the lab.

On Normal difficulty the common attacks take 12 health, so five hits end a life. The range runs from 12 to 32, and the single biggest attack, type 32, takes 48 and leaves 8 health. Touching an enemy costs 1 health, and so does a projectile, except two projectile types that cost 10.

Your own side of the trade is smaller numbers over more hits. A jab takes 1 health, a thrown enemy or prop takes 4, and an enemy that touches you loses 1 health as well. The bosses, in jab hits:

How to read this. One bar per boss, its length the boss's health. Because a jab takes exactly 1, the number is also the count of jab hits needed. The second line under a name is where the boss appears ("mid" is a mid-level boss, "end" the last boss of the level).

Hover a bar for the thrown-prop count (4 health per hit). Some bosses cannot be grabbed (the armoured cyborg is one), so props and ordinary grabbable enemies are the only way to use the 4.

Takeaway. The economy is lopsided on purpose: enemies hit rarely and hard, the player often and lightly. Five clean hits end your life on Normal, while the strongest boss here needs 48 of yours, so the fight is about not getting hit rather than about trading.

  • measuredThere is no invulnerability after being hit. A second attack that lands 8 frames after the first is a second hit, which is why one thug animation can deal 36.
  • measuredAn enemy that takes a hit is stunned for 15 frames and does not move. You flinch for 16.
  • measured83 of 83 health decrements in a damage log matched 4 × table for melee, 1 for contact and 1 or 10 for projectiles.
  • readThe one health pickup is a pool A object that restores 8 and only works below 48 health.
  • readYou do blink, and cannot be hurt, for 320 frames after joining, respawning or continuing, and for 20 frames after getting up from a knock-down. Nothing in the program awards an extra life.

Played through, not only read

A bot reads the same RAM the enemies do and plays each level from its start with only the health cell held up (and the level timer refilled, which is noted per level). It uses the moves above. Where it stalled, the cause was usually geometry the earlier lab work had not met. Only level 1 is cleared; the other rows say how far the runs got.

How to read this. The bot is a Lua script running inside MAME that presses the buttons a player would. "Health cell held up" means it keeps writing the player's health byte back to full, so it cannot die from damage; everything else, including every enemy decision, is the game's own. Its targeting uses the box rule from the top of this page: it attacks only when its jab box would overlap the target's body box. "Scroll" is how far the screen has scrolled into the level, in pixels (hexadecimal). A green pill means the level was cleared, amber that the run got part of the way.
{{NATROWS}}
  • measuredLock walls are not unbreakable. Standing against the level 1 rubble wall and jabbing breaks it within about 150 frames, so no prop has to be carried.
  • measuredLadders are narrow doors. In level 4 the descent accepts a plain down press only between x 1502 and 1506, five pixels, and 1501 or 1507 does nothing.
  • readA wall tile can stop a walking player. At the end of level 2 the player halts at x 2291, 12 px short of a tile column at x $900 (terrain attribute $e800), and the level 4 lower floor halts the same way at x 1779. Whether a jump clears them has not been tested yet.
  • measuredThe level timer starts at 300 and loses one per 63 frames, so about 18,900 frames per life. It kills in god mode too, so a stalled bot dies at frame 19,800.

Takeaway. The rules read from the code were good enough to fight with: a bot that only knows the hit boxes and the moves gets through real levels. What stopped it was terrain, such as walls and ladders, which this page does not model.
